## Bounded polling ownership follow-up

There is no existing `productionHierarchyBootstrapped` flag. `BootstrapProductionHierarchy` synchronously reads every immutable pack record, submits each upload batch, waits the graphics queue idle, calls `CompleteProductionUploads`, and validates the full lookup plus terrain bindings before entering the normal frame loop (`NovaCoreNative.cpp:1150–1185`, call at 2498). The current `productionRootsReadyLogged` flag proves only that six roots were logged, not the full hierarchy transaction. `ProductionHierarchyPayloadsReady` scans lookup entries and is the current full-hierarchy predicate; it does not independently prove all shared terrain keys still describe the same domain.

`productionLayerLastUse` has writes but no read/eviction consumer in current native source. Thus the first queue scan's last-use maintenance has no current replacement-policy consumer. The second scan combines actual request generation and key-state repair. Production `planetary_select.comp:129` addresses immutable slots by ordinal and only writes the use/transition words; its non-production branch at 144–145 can evict and overwrite shared keys. Pack presence alone is therefore too broad a reason to skip every future scan across generic contexts. Generic/non-Earth startup without a production pack already exits the queue function immediately.

The worker lifetime also matters. `ProductionIoWorker` at 1071 pops a request and releases the mutex while reading the pack; its result appears in the ready array later. Empty `requestCount` and an empty ready array do **not** prove no in-flight read. No explicit in-flight counter exists. Stopping only request discovery must still complete pending uploads and consume already issued work, unless the proposed immutable transaction proves none was ever issued. Destruction at 1095 sets stop, notifies, joins and only then releases the pack/resources. A correction must not weaken that ownership.

A narrow next measurement, if authorized by the fresh CPU result, is the queue scan's own host duration and request/upload state in the normal production route. Do not yet remove the worker, change cache policy, or add generic resource architecture. The observation above is source causality and a potential guard requirement, not proof of >=1.5 ms recoverable cost.

## Fresh CPU evidence and cached-key candidate screen

Subsequent `poll-florida.json` and `poll-orbital.json` isolate the unchanged request queue function. In their 100 steady frames (Florida 182–281; orbital 82–181), the arithmetic midpoint medians are 1.9143 ms and 1.8865 ms; nearest-rank P99 values are 2.0765 ms and 1.9866 ms. Every selected row has requests=0, pending=0, uploads=126. The allocation trace proves the 393,216-byte key buffer uses compatible type 1, flags 6, while compatible type 3 has flags 14. These are respectively coherent mapped uncached and coherent mapped cached host memory on this machine. This is an isolated recurring CPU cost; a replacement's recoverable time is still pending A/B measurement.

The proposed narrow control changes only the key buffer's memory preference to HOST_CACHED while continuing to require HOST_VISIBLE, HOST_COHERENT and `memoryTypeBits` compatibility. It preserves all scans, CPU and GPU writes, worker activity, barriers/fences, bindings, allocation count, capacity and lifetime. The six M13.5 GPU working-set roles remain unchanged. This is substantially narrower than poll elision because it requires no quiescence assumption or newly cached hierarchy/domain state.

[The Vulkan memory-property specification](https://docs.vulkan.org/refpages/latest/refpages/source/VkMemoryPropertyFlagBits.html) distinguishes host caching from host coherence: cached memory accelerates host access; coherence removes explicit host cache-management requirements. Neither removes the need for existing execution and memory synchronization. Require cached **and coherent**, not cached instead of coherent. Preference failure must retain the original compatible coherent host fallback; never select an incompatible type, reinterpret device-local preference for the six banked roles, or retry device/validation errors as capacity failure.

The ticket's >=1.5 ms payoff clause does not restrict its unit to GPU time. It separately requires net CPU/GPU improvement and that CPU submission/update not become a terrain limiter. A repeatable >=1.5 ms recovery in actual normal displayed-frame CPU duration, with no GPU/output regression, is therefore a substantive CPU candidate under those clauses. It must be described as CPU frame recovery. It cannot be subtracted from total GPU time, cannot claim Florida now meets 8.33 ms GPU, and cannot relax that objective. The ticket's preferred result of bringing a GPU-failing regime under 8.33 ms would remain unmet by a CPU-only correction.

The strongest pending attack is cost migration: cached A/B must recover >=1.5 ms outside diagnostic logging and outside a scope merely reassigned to fence time, while retaining GPU-key-access performance and normal cadence. Validate generic and production key producers, ordinary runtime startup, dynamic transitions, exact prepared/selected/raster output at controlled inputs, and strict Vulkan reporting. Policy checks should cover cached type incompatibility, cached-but-noncoherent exclusion, unavailable preference, UMA same-type no-repeat, capacity/map failure fallback and non-capacity fatal errors. The 1.9 ms scan measurement by itself is not final qualification.

The smallest design adds one explicit coherent cached CPU-read use to the existing enum and opts in only the terrain-key allocation. All six banked GPU-use call sites and their selector behavior must remain unchanged.

The existing preference helper already maps a tentative allocation before binding it, frees a failed-map allocation before fallback, retries only capacity/map errors, avoids retrying the same type, and reports bind/non-capacity errors. Reuse that mechanism. A cached preference must not require a new memory type on unsupported devices or silently admit HOST_CACHED without HOST_COHERENT. No second key copy, allocation, polling schedule, data layout, descriptor, dirty flag, worker cancellation or source of authority is necessary.
